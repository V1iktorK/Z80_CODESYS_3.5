# 05. АППАРАТНЫЙ ВВОД/ВЫВОД И DEVICE TREE

## 1. Как устроена связь Z80 с физическими входами/выходами ПЛК

Задача: инструкции `IN`/`OUT` Z80 должны читать и писать **реальные** каналы ПЛК.

Наивное решение — обращаться к `%IX`/`%QX` прямо из инструкции — неверно, и вот
почему. **Инструкция Z80 исполняется внутри скана**, а физические входы ПЛК
обновляются только на **границе скана**. Если читать `%IX` посреди скана, значение
может «плавать»: часть инструкций увидит старое состояние, часть — новое. Это
классическая гонка между скан-циклом ПЛК и эмуляцией процессора.

**Решение — двойная буферизация.** Все внешние данные проходят через буферы:

```
   нач. скана                                    кон. скана
       │                                              │
       ▼                                              ▼
  %IX0.0..7 ──► FB_HW_IO_PLC ──► GVL_HW_Buffer ──► Z80: IN ──► …
                                                    Z80: OUT ──►
  %QX0.0..7 ◄── FB_HW_IO_PLC ◄── GVL_HW_Buffer ◄───────────────┘
```

| Сеть PLC_PRG | Что происходит |
|---|---|
| **15** | `FB_HW_IO_PLC` читает `%IX`/`%IW`, упаковывает дискретные входы в байт, кладёт в `GVL_HW_Buffer` |
| **16** | `FB_IO_Ports` обслуживает `IN`/`OUT`: читает из буферов, пишет в них |
| **15d** | выходы `DO_0..DO_7` уходят на физические `%QX0.0..%QX0.7` |
| **15e/f** | аналоговые выходы уходят на `%QW0`/`%QW1` |

**Почему так правильно:** внутри скана эмулятор работает только с буферами, и
поведение становится полностью детерминированным — не зависит от того, в какой
момент runtime ПЛК обновил `%I`. Обмен с «живым» железом происходит строго в
начале и в конце скана.

## 2. Карта портов Z80

| Порт | Напр. | Что делает | Привязка |
|---|---|---|---|
| `00h` | IN | дискретные входы ПЛК | `%IX0.0..%IX0.7` |
| `01h` | OUT | дискретные выходы ПЛК | `%QX0.0..%QX0.7` |
| `02h` | IN | аналоговый вход 0, младший байт | `%IW0` (биты 0..7) |
| `03h` | IN | аналоговый вход 0, старший байт | `%IW0` (биты 8..15) |
| `04h` | OUT | аналоговый выход 0, младший байт | `%QW0` |
| `05h` | OUT | аналоговый выход 0, старший байт | `%QW0` |
| `06h`/`07h` | IN | аналоговый вход 1 | `%IW1` |
| `08h`/`09h` | OUT | аналоговый выход 1 | `%QW1` |
| `10h` | IN | консоль CP/M: статус (bit 0 = есть символ) | `GVL_CPM.Console_InEn` |
| `11h` | IN | консоль CP/M: принять символ | `GVL_CPM.Console_In` |
| `12h` | OUT | консоль CP/M: вывести символ | `GVL_CPM.Console_Out` |
| `20h` | OUT | управление: bit 0 = запрос HALT | `FB_IO_Ports.Halt_Req` |
| `21h` | IN | состояние: bit 0 = CP/M загружен | `GVL_CPM.Cpm_Loaded` |

## 3. Объявления переменных ввода/вывода

Физическая привязка сделана атрибутом `AT` — **в программе `PLC_PRG`**
(`src/PLC_PRG.plcopenxml`; объявления создаёт `generator/gen_z80.py`):

```iecst
PROGRAM PLC_PRG
VAR
    (* --- дискретные входы: IN 00h читает этот байт --- *)
    PLC_DI_0 AT %IX0.0 : BOOL;
    PLC_DI_1 AT %IX0.1 : BOOL;
    ...
    PLC_DI_7 AT %IX0.7 : BOOL;

    (* --- дискретные выходы: OUT 01h пишет этот байт --- *)
    PLC_DO_0 AT %QX0.0 : BOOL;
    ...
    PLC_DO_7 AT %QX0.7 : BOOL;

    (* --- аналоговые: IN 02h/03h и OUT 04h/05h --- *)
    PLC_AI_0 AT %IW0 : INT;
    PLC_AI_1 AT %IW1 : INT;
    PLC_AO_0 AT %QW0 : INT;
    PLC_AO_1 AT %QW1 : INT;
END_VAR
```

> **Почему в `PLC_PRG`, а НЕ в `GVL`.** В списке глобальных переменных
> (`VAR_GLOBAL`) директива `AT` **запрещена**: CODESYS выдаёт 40 ошибок
> `C6: ';, :=, REF=, ( или [' требуется вместо 'AT'`. Это ограничение
> диалекта. В `PROGRAM` тот же `AT` работает штатно.
> Раньше в этом документе было написано «привязка в `GVL_HW_IO`» — так
> сделать нельзя, и текст исправлен.

Порядок в объявлении с адресом строгий: **имя → `AT` → адрес → двоеточие →
тип**. Записать адрес после типа (`PLC_DI_0 : BOOL AT %IX0.0`) нельзя —
именно это и даёт ошибку `C6`.

### Что означают 20 предупреждений «Адрес %IX0.0 не задан ни в одном устройстве»

Это **не дефект кода**. Проект стоит на `CODESYS Control Win V3` (SoftPLC),
у которого физических каналов нет, поэтому CODESYS сообщает, что адрес не
принадлежит ни одному устройству дерева. На реальном ПЛК с модулями
ввода-вывода эти сообщения исчезают сами: адреса совпадут с каналами
модулей. Проверено обратное: если убрать `AT`, предупреждения уходят, но
вместе с ними исчезает и привязка к железу — то есть требование задания.
Поэтому привязка оставлена.

## 4. Настройка Device Tree в CODESYS

**Сейчас в проекте стоит `CODESYS Control Win V3`** — это SoftPLC, работающий
на том же компьютере. Он полезен для отладки, но **физических каналов у него
нет**: адреса `%IX0.0`/`%QX0.0` в нём объявлены, но ни к чему не привязаны.
Именно поэтому код сразу проверяется в режиме симуляции, а железо подключается
отдельным шагом.

### Шаг 1. Заменить устройство на реальный ПЛК

1. Правый клик на узле `PLCWinNT` → **Update Device…**
2. Выбрать свой ПЛК (например `CODESYS Control RTE V3` для Windows-ПК с
   реальным временем или устройство производителя ПЛК).

Для ПЛК производителя (Owen, ОВЕН СПК, Schneider M262, WAGO и т. п.)
устройство добавляется из репозитория: в **Device Repository** нужно
установить пакет поддержки, после чего устройство появится в списке.

### Шаг 2. Добавить модули ввода/вывода

1. Правый клик на устройстве → **Add Device…**
2. Выбрать модуль дискретных входов → он появится под устройством.
3. Повторить для модулей: дискретные выходы, аналоговые входы, аналоговые
   выходы.

### Шаг 3. Проверить раскладку каналов

Открыть вкладку **I/O Mapping** каждого модуля. Адреса вида `%IX0.0`,
`%QX0.0`, `%IW0`, `%QW0` назначаются автоматически по порядку модулей в
дереве. **Если порядок другой — адреса в `GVL_HW_IO` надо привести в
соответствие.** Это единственное место, которое зависит от конкретного железа.

### Шаг 4. Привязать переменные

В **I/O Mapping** для каждого канала в колонке *Variable* указать нашу
переменную:

| Канал модуля | Переменная |
|---|---|
| DI 0 модуля | `PLC_PRG.PLC_DI_0` |
| DI 1 модуля | `PLC_PRG.PLC_DI_1` |
| … | … |
| DO 0 модуля | `PLC_PRG.PLC_DO_0` |
| AI 0 модуля | `PLC_PRG.PLC_AI_0` |
| AO 0 модуля | `PLC_PRG.PLC_AO_0` |

CODESYS подставит эти переменные автоматически, если адреса совпадают с
объявленными `AT`. Достаточно проверить, что привязка не пустая.

**Почему это работает без правки схемы:** весь обмен с железом изолирован в
`FB_HW_IO_PLC`. Схема процессора ничего не знает о конкретном ПЛК — она видит
только `GVL_HW_Buffer`. Поэтому перенос проекта на другое железо сводится к
смене устройства и проверке адресов, а не к перерисовке схемы.

## 5. Проверка без железа

Пока реального ПЛК нет, весь путь ввода/вывода проверяется в симуляции:

1. Запустить симуляцию, войти в онлайн.
2. В Watch-окне открыть `PLC_PRG` и задать `PLC_DI_0 := TRUE`,
   `PLC_DI_2 := TRUE`, `PLC_DI_5 := TRUE`, `PLC_DI_7 := TRUE`
   (это даёт байт `A5h`), `PLC_AI_0 := 16#1234`.

   Для SoftPLC-симуляции это самый прямой путь: значения, записанные в
   `%IX`/`%IW`, попадают в схему ровно так же, как попали бы с реального
   модуля ввода. Ветка через `GVL_HW_IO` (тестовый образ входов) при этом
   остаётся доступной — если `AT`-переменные не заданы, схема берёт данные
   из `GVL_HW_IO`.
3. Установить `GVL_Tests_CPM.Cpm_Test_Run := TRUE`.
4. Тесты `IO01`, `IO03`, `IO04`, `HW01`, `HW02` проверят, что эти значения
   дошли до шины I/O и до буферов.

Именно так проверяются тесты группы `IO`/`HW` в `TEST_Z80_CPM` — они не
требуют железа, потому что работают через те же буферы, что и реальный тракт.
