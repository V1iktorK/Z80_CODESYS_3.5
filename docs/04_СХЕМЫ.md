## Главная схема: конвейер из 14 сетей

`PLC_PRG` соединяет блоки в конвейер. Порядок сетей **и есть** порядок
исполнения — отдельный Execution Order в FBD не нужен.

| № | Сеть | Что делает |
|---:|---|---|
| 1 | TAkT | `FB_Clock` формирует `Clk_Decode` и `Clk_Exec` |
| 2 | PC | `fbPCLatch.Q` → `GVL_Bus.Bus_Addr` |
| 3 | FETCH | код команды защёлкивается в `fbIR` по `Clk_Decode` |
| 4 | ДЕКОДЕР | `fbDec` разворачивает IR в 16 сигналов |
| 5 | ЧТЕНИЕ RF | `fbRFRd` читает операнды (без записи) |
| 6 | АДРЕС | выбор `(HL)` или `nn`, плюс сборка адреса `nn` |
| 7 | ПОРТ ОПЕРАНДА | `fbMem` читает/пишет по вычисленному адресу |
| 8 | ALU | `fbALU` считает результат и флаги |
| 9 | ФЛАГИ | `fbFlags` запоминает F |
| 10 | ЗАПИСЬ RF | `fbRF` записывает результат в регистр |
| 11 | СТЕК | `fbSP` обслуживает CALL/RET |
| 12 | УПРАВЛЕНИЕ | `fbCtl` выбирает следующий PC |
| 13 | PC | `fbPC` + защёлка `fbPCLatch` |
| 14 | R | `fbR` инкрементируется каждую команду |

### Почему регистровый файл вызывается дважды

Один вызов дал бы кольцевую зависимость `RF → ALU → RF` внутри скана.
Поэтому стоят **два экземпляра** `FB_RegFileZ80`:

* `fbRFRd` — только чтение (`Wr_En = FALSE`), стоит в сети 5;
* `fbRF` — только запись, стоит в сети 10.

Так кольцо разрывается, и порядок вычислений становится однозначным.

## Как реализовано состояние в FBD

В FBD нет элемента «регистр». Состояние хранится **обратной связью**: выход
блока заводится на его вход. Базовый приём, повторяющийся во всех регистрах:

```
        SEL ──────────────► Q
     G ─┘  │
          └──────────────┐     ← эта обратная связь и есть память
                         │
        Q ───────────────┘
```

`G = FALSE` → на выход идёт `Q` (предыдущее значение) → состояние сохраняется.
`G = TRUE` → на выход идёт `IN1` (новое значение) → состояние обновляется.

**Следствие:** любая такая схема даёт задержку в один скан. Именно поэтому
принят двухфазный такт: на фазе декодирования читается предыдущее состояние,
на фазе исполнения записывается новое.

## Двухфазный такт

`FB_Clock` формирует два непересекающихся импульса за скан:

| Фаза | Сигнал | Что делает |
|---|---|---|
| 1 | `Clk_Decode` (`FB_RTrig`) | PC → память → IR, декодирование |
| 2 | `Clk_Exec` (`FB_FTrig`) | ALU, запись результата, PC, SP, флаги |

Зачем: наивная схема даёт комбинационную петлю
`PC → память → ALU → флаги → PC`, которую CODESYS либо отвергнет, либо
исполнит недетерминированно. Триггер разрывает петлю. Требование
«один скан = одна команда» сохраняется — команда выполняется в два полутакта
внутри скана.

## АЛУ: как считаются флаги

**Перенос и заём** берутся из 16-битной суммы: `S := WORD(A) + WORD(B)`,
тогда перенос из бита 8 — это бит 0 старшего байта. **Заём** при вычитании
есть в точности отсутствие переноса при сложении (`Sub_C := NOT Add_C`).

**Полуперенос (H)** — перенос из бита 3 в бит 4, по учебной формуле:

```
H := ((A AND 0Fh) + (B AND 0Fh)) AND 10h  <>  0
```

Складываем младшие тетрады и смотрим, перешли ли через границу тетрады.
Сравнение с нулём обязательно: без него получается байт, а не признак.

> **Здесь была ошибка.** Раньше стояло
> `H := (A.3 AND B.3) OR (B.3 AND NOT Y.3) OR (NOT Y.3 AND A.3)`.
> Это не полпереноса, и вдобавок смешивало типы `BYTE` и `BOOL`.
> Исправлено на этапе 7 (дефект 42 в журнале сборки).

**P/V** имеет два разных смысла в одном бите:

| Операции | Правило |
|---|---|
| AND / OR / XOR | чётность: `P/V := (XOR всех 8 бит результата) = 0` |
| ADD / SUB / CP | переполнение со знаком: `(A.7 = B.7) И (A.7 ≠ Y.7)` для ADD, `(A.7 ≠ B.7) И (A.7 ≠ Y.7)` для SUB |

> **Здесь тоже была ошибка.** Раньше чётность считалась как `NOT` байта:
> `NOT` над байтом даёт `0FFh`/`0FEh`, а не логический ноль/единицу, и тип
> не совпадал с объявленным `BOOL`. Исправлено (дефект 43).

**Флаги при `INC`/`DEC`.** В Z80 они меняют H, P/V, N, но **не трогают C**.
В схеме `INC`/`DEC` — это `ADD`/`SUB` с единицей (для этого в ALU есть вход
`B_Forced` и признак `IncDec`), а бит C в регистр флагов не записывается:
вместо него подаётся прежнее значение `F.0`.

## Имена выводов: почему они такие

Выяснено экспериментально:
1. Импорт падает с «Отсутствует обязательный атрибут formalParameter», если у
   **любого** входа не указано имя вывода. Пустая строка не годится.
2. При этом CODESYS сопоставляет выводы **по позиции** — конкретные имена не
   важны. Используем традиционные `IN1`/`IN2`/`IN`.
3. При экспорте CODESYS переименовывает их в канонические `In1`/`In2`/`Out1`.

Входы `FB_FlagsRegZ80` названы с префиксом `Flag_` (`Flag_S`, `Flag_C`, …),
потому что односимвольные `S` и `C` в IEC 61131-3 зарезервированы под типы
(`SINT`, `INT`) и компилятор их отвергает с ошибкой `C9`.

## Типы в FBD: главное правило проекта

В IEC 61131-3 многие блоки **обобщённые** (`ANY`): `AND`, `OR`, `XOR`, `NOT`,
`ADD`, `SUB`, `SHL`, `SHR`, `EQ`, `NE`, `SEL`, `MUX`. Их тип выводится по
операндам. Если рядом оказываются операнды разных типов, CODESYS выбирает
`USINT` и потом не может согласовать результат с объявленным типом.

Сообщения при этом не содержат ни имени POU, ни номера сети:

```
C32: Невозможно конвертировать тип 'BOOL'  в тип 'USINT'
C32: Невозможно конвертировать тип 'USINT' в тип 'BOOL'
C32: Невозможно конвертировать тип 'BOOL'  в тип 'BYTE'
C32: Невозможно конвертировать тип 'WORD'  в тип 'BYTE'
```

Отсюда правило, которое в проекте применяется **системно**:

> Выход обобщённого блока перед обобщённым потребителем проводится через
> **явную переменную нужного типа**. Тогда тип закрепляется объявлением
> POU, и согласование становится однозначным.

Пример из `FB_ALU_Z80` (сеть 2 → сеть 3):

```
вихід AND/OR/XOR  →  Logic_And / Logic_Or / Logic_Xor : BYTE  →  SEL
```

И частные следствия:

* **Безтиповые литералы недопустимы в обобщённых входах.** Вместо `0`
  пишется `BYTE#0`, вместо `1` в булевом месте — `TRUE`.
* **`BOOL` и число нельзя смешивать в одном блоке.** `AND(флаг, 16#01)` —
  ошибка и по типу, и по смыслу; нужен либо сам флаг, либо сравнение.
* **Конверсию в себя писать нельзя** — `BYTE_TO_BYTE` в CODESYS не
  существует (это отдельная ошибка `C46`).
* **Признак — это сравнение, а не маска.** `Y AND 16#80` даёт байт
  (`16#80`/`16#00`), а нужен `BOOL`: `(Y AND 16#80) = 16#80`.
* **В одном выражении не должно быть разных типов.** `Z80_Mem[nPtr + 32 * i]`,
  где `nPtr` — `WORD`, а `i` — `INT`, даёт
  `C196: неявная конверсия WORD → INT: возможно изменение знака` — без имени
  POU и номера строки. Индексация приводится к одному типу:
  `Z80_Mem[nPtr + SHL(INT_TO_WORD(i), 5)]`.
* **Граница цикла — числом, а не выражением.** `FOR i := 0 TO 64 * 32 - 1`
  даёт у границы тип `UINT` и неявную конверсию к `INT`-счётчику. Пишется
  `FOR i := 0 TO 2047`.
* **`WORD`-индекс в массив 64 КБ — можно.** Проверено отдельным опытом
  (`generator/tools/probe_index.py`): `Z80_Mem[w]`, где `w : WORD`,
  компилируется без предупреждений. Массив `ARRAY[0..65535]` принимает индекс
  любого числового типа. Ошибка возникает только при **смешении** типов
  внутри одного выражения.
* **Неиспользуемый вход опасен.** `<inVariable>`, на который никто не
  ссылается, CODESYS превращает в оператор без действия и выдаёт `C139`.
  Библиотека такие входы удаляет в `Pou.render()`; делать это по отдельной
  сети нельзя — `localId` уникальны в пределах всего POU.

Проверяется автоматически: `generator/tools/find_mixed_ops.py`
(рекурсивно выводит типы через блоки, выходы экземпляров FB и переменные GVL)
и тесты `T9`/`T10` в `generator/tools/tests_plan.py`.

## Fan-out: главное ограничение и как оно обойдено

**CODESYS 3.5 SP17 молча выбрасывает POU целиком**, если выход любого элемента
питает больше одного входа. Никакой ошибки при импорте не возникает — объект
просто не появляется в дереве проекта. Именно так был потерян `FB_ALU_Z80`.

Библиотека `fbd_xml.py` лечит это клонированием ветвей, но эксперимент показал,
что у клона может остаться **неподключённый вход**. Поэтому в схемах принято
правило:

> Каждое потребление сигнала — **отдельный экземпляр** входной переменной.

Тогда клонирование вообще не запускается, и схема переносится один в один:

```
СГЕНЕРИРОВАНО : блоков=448 связей=974 пустых.входов=0
ПОСЛЕ ИМПОРТА : блоков=448 связей=974 пустых.входов=0
```

Отдельное следствие для вызовов FB: **экземпляр вызывается ровно один раз за
скан**, а его выходы читаются по имени (`fbPC.PC_Next`). Если выход нужен
дважды — сигнал проводится через локальную переменную POU.

## Правило типизации цепочек выбора (SEL)

Цепочка `SEL` — основной способ сделать выбор «одно из многих» в FBD:
каждый блок берёт очередное значение, если сработало его условие, иначе
пропускает дальше предыдущий результат. Так собраны выборка регистра чтения,
чтение I/O-порта и начальные значения регистров.

**Правило: каждая ветвь такой цепочки должна иметь тип, известный
компилятору заранее.**

Почему это важно. `SEL` — обобщённый блок (IEC `ANY`): его тип CODESYS
выводит по ветвям `IN0`/`IN1`. Если одна ветвь — переменная типа `BYTE`,
а другая — «голый» литерал `0` или `16#00`, компилятор **сам выбирает тип
литерала**. В цепочке из десятка блоков он выбирает `USINT` для всех,
и дальше сборка падает сообщениями без имени POU и номера сети:

```
C32: Невозможно конвертировать тип 'BOOL'  в тип 'USINT'
C32: Невозможно конвертировать тип 'USINT' в тип 'BOOL'
C32: Невозможно конвертировать тип 'BOOL'  в тип 'BYTE'
C32: Невозможно конвертировать тип 'WORD'  в тип 'BYTE'
```

Поэтому в схемах:

| В ветви `SEL` | Как записано |
|---|---|
| константа-байт | `BYTE#0`, `BYTE#16#00`, `BYTE#16#FF` |
| константа-слово | `WORD#16#FA23` и т. п. |
| строб «есть/нет» | `SEL(G, BYTE#0, BYTE#1)` — см. ниже |
| переменная POU | как есть: тип задан объявлением |
| выход конверсии | как есть: тип задан самой конверсией |

Две вещи, которых в схемах **сознательно нет**:

1. **`BOOL_TO_BYTE`.** В CODESYS эта конверсия даёт `USINT`, а не `BYTE`
   (для `BYTE` — битовой строки — обобщённые блоки выводят `USINT`).
   Такой выход, попав в цепочку `BYTE`, ломает её тип. Поэтому строб
   «есть символ / нет символа» собирается блоком `SEL` с двумя явными
   литералами `BYTE#0` и `BYTE#1` — тип результата однозначен.
2. **`BYTE_TO_BYTE`.** В CODESYS такой функции не существует; попытка
   «привести ветвь к тому же типу» ею даёт 76 ошибок
   `C46: Идентификатор 'BYTE_TO_BYTE' не задан`. Приводить ветви не нужно —
   достаточно явно записать литерал.

Проверка автоматическая: `tools/find_sel_types.py` рекурсивно выводит типы
ветвей каждого `SEL` во всех схемах и сообщает, где они разные. Тест плана
**T8** держит это закрытым.

Пример из `FB_IO_Ports` (чтение порта `10h`, статус консоли):

```
        ┌─────────────┐
Con_Rdy─┤G            │
 BYTE#0─┤IN0   SEL   OUT├──► ветвь цепочки (BYTE)
 BYTE#1─┤IN1          │
        └─────────────┘
```

Обе ветви — `BYTE`, условие — `BOOL`, результат — `BYTE`.
